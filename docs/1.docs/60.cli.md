# CLI

> Nitro 提供了 `nitro` 命令，用于开发、构建、预览和部署项目。

当 `nitro` 作为项目依赖安装时，通过包管理器运行它（`npx nitro`、`pnpm nitro`、`yarn nitro`、`bun nitro`、……），或者将其添加到 `package.json` 脚本中：

```json [package.json]
{
  "scripts": {
    "dev": "nitro dev",
    "build": "nitro build",
    "preview": "nitro preview"
  }
}
```

然后按照[快速开始](/docs/quick-start)指南中的说明使用 `npm run dev`、`pnpm dev` 等命令。

::tip
每个命令都支持使用 `--help` 查看其参数概览（例如 `nitro build --help`），而 `nitro --version` 会打印已安装的 Nitro 版本。
::

除 `nitro create` 外，所有命令都接受项目根目录，可将其作为位置参数（`nitro build ./my-app`）传入，也可以使用 `--dir` 标志（推荐）。默认使用当前目录。`nitro fetch` 只接受 `--dir`，因为它的位置参数是 URL。

::note
将 Nitro 用作 [Vite 插件](/docs/vite)？建议使用 Vite CLI（`vite dev`、`vite build`、`vite preview`）；Nitro 开发服务器不支持 Vite builder。
::

## `nitro create`

根据模板创建新的 Nitro 项目。模板随 Nitro 一同提供，无需下载；新项目中的 `nitro` 依赖会设为执行创建命令的 Nitro 版本。

```sh
npx nitro create [dir] [--template <template>] [--packageManager <name>] [--no-install] [--gitInit] [--force]
```

| 标志 | 描述 |
| --- | --- |
| `dir` | 创建项目的目录（默认为 `nitro-app`；AI agent 未指定 `--template` 时必填）。 |
| `--template`、`-t` | 按构建器选择项目模板：`vite`（带前端的全栈应用）、`rolldown`（生产环境打包的 API 服务器）、`rspack`（使用 [Rspack](/config/build#builder) 打包的 API 服务器，实验性），或 `runtime`（不执行构建步骤的 API 服务器，使用 [`builder: false`](/config/build#builder)，实验性）。 |
| `--packageManager`、`-p` | 用于安装依赖的包管理器（`npm`、`pnpm`、`yarn`、`bun`、`deno` 等）。 |
| `--no-install` | 跳过依赖安装。 |
| `--gitInit` | 初始化 git 仓库。 |
| `--force` | 写入非空目录，并覆盖模板创建的文件（仅包含 `.git` 的目录视为空目录）。 |

在交互式终端中运行时，`nitro create` 会提示输入尚未通过标志设置的选项。否则，它会在 `nitro-app/` 中创建 `vite` 模板，使用运行该命令的包管理器（或 `npm`）安装依赖；如果目录非空，则会失败。

未知选项、未提供值的选项和多余参数都会被拒绝。AI agent 未指定目录或模板时，命令会输出可用选项并退出，以便 agent 明确选择。完成后，命令会输出创建内容摘要（目录、模板、包管理器、依赖和 git），然后列出后续步骤；即使依赖安装失败，也会输出这些信息。

**示例：**

```sh
npx nitro create my-api --template rolldown --packageManager pnpm
```

## `nitro dev`

启动支持热重载的开发服务器。

```sh
npx nitro dev [--dir <dir>] [--port <port>] [--host <host>] [--envName <name>]
```

| 标志 | 描述 |
| --- | --- |
| `--dir` | 项目根目录。 |
| `--port` | 要监听的端口。 |
| `--host` | 要监听的主机名。 |
| `--envName` | 用于应用 `$env.<name>` 配置覆盖项并通过 `import.meta.envName` 暴露的[环境名称](/docs/configuration#environment-specific-config)（默认为 `development`）。 |

开发服务器会监视 Nitro 配置：对 `runtimeConfig` 或 `routeRules` 的更改会热重载，而其他配置更改会触发开发服务器完全重启。

在浏览器中打开的 HTML 错误页（5xx）会在修复并重新加载服务器后自动刷新，使用 [Vite 插件](/docs/vite)时也一样。该页面会等待 `/_nitro/dev/reload` 路由（位于 `baseURL` 下）；此路由在开发模式中保留使用。

**示例：**

```sh
npx nitro dev --port 4000 --host 0.0.0.0
```

## `nitro build`

为生产环境构建项目。Nitro 会准备构建目录、复制公共资源、预渲染所有已配置的路由，并将服务器打包到输出目录（默认为 `.output/`）。

```sh
npx nitro build [--dir <dir>] [--preset <preset>] [--minify] [--builder <builder>] [--compatibility-date <date>] [--envName <name>]
```

| 标志 | 描述 |
| --- | --- |
| `--dir` | 项目根目录。 |
| `--preset` | 要构建的部署[预设](/deploy)（也可以使用 `NITRO_PRESET` 环境变量）。 |
| `--minify` | 压缩输出，覆盖预设默认值。使用 `--no-minify` 可禁用压缩。 |
| `--builder` | 要使用的打包器：`rollup`、`rolldown`、`rspack`、`vite` 或 `bun`（也可以使用 `NITRO_BUILDER` 环境变量）。 |
| `--compatibility-date` | 预设兼容性日期（也可以使用 `NITRO_COMPATIBILITY_DATE` 环境变量）。 |
| `--envName` | 用于应用 `$env.<name>` 配置覆盖项并通过 `import.meta.envName` 暴露的[环境名称](/docs/configuration#environment-specific-config)（默认为 `production`）。 |

**示例：**

```sh
npx nitro build --preset cloudflare_module
```

### `NITRO_PRESET` 与 `--preset`

两者都会设置部署 preset，而 `--preset` 标志的优先级高于 `NITRO_PRESET` 环境变量。在部署平台和 CI 中，环境变量非常方便，因为你通常无法更改构建命令：

```sh
NITRO_PRESET=cloudflare_module npm run build
```

## `nitro preview`

启动本地服务器，以预览生产环境构建输出。

```sh
npx nitro preview [--dir <dir>] [--port <port>] [--host <host>]
```

| 标志 | 描述 |
| --- | --- |
| `--dir` | 项目根目录。 |
| `--port` | 要监听的端口。 |
| `--host` | 要监听的主机名。 |

**示例：**

```sh
npx nitro build
npx nitro preview
```

## `nitro serve`

直接从项目源文件启动服务器，不执行构建步骤（别名：`nitro start`）。

```sh
npx nitro serve [--dir <dir>] [--port <port>] [--host <host>] [--dev] [--envName <name>]
```

| 标志 | 描述 |
| --- | --- |
| `--dir` | 项目根目录。 |
| `--port` | 要监听的端口（默认依次使用 `NITRO_PORT` 或 `PORT` 环境变量，然后是 `3000`）。 |
| `--host` | 要监听的主机名（默认使用 `NITRO_HOST` 或 `HOST` 环境变量）。 |
| `--dev` | 以开发模式启动，与不使用构建器的 `nitro dev` 类似。 |
| `--envName` | 用于应用 `$env.<name>` 配置覆盖项并通过 `import.meta.envName` 暴露的[环境名称](/docs/configuration#environment-specific-config)（默认为 `production`；指定 `--dev` 时为 `development`）。 |

无论配置了什么构建器，服务器都会在生产模式下不使用构建器运行（[`builder: false`](/config/build#builder)）：文件会直接在服务器进程中运行，公共资源则从源目录提供。使用 [`buildPlugins`](/config/build#buildplugins) 时，由于插件钩子可能是异步的，服务器会改为运行在自行监听端口的 Node.js worker 中。此模式支持 WebSocket 处理器和定时任务。环境变量会从 `.env.production` 和 `.env` 文件中加载，但不会覆盖现有值。

收到 `SIGINT` 或 `SIGTERM` 时，服务器会停止接受连接，等待正在处理的请求完成，并在退出前运行 `close` 钩子。如果服务器（或其 worker）意外退出，命令会以代码 `1` 退出，以便进程管理器重新启动它。

::warning
不使用构建器运行目前处于实验阶段。打包器选项和通过 `build:config` 钩子添加的插件不会生效，详情请参阅 [`builder`](/config/build#builder)。
::

**示例：**

```sh
npx nitro start --port 8080
```

## `nitro fetch`

从项目源文件启动服务器并发送单个请求，不执行构建步骤；打印响应后退出（别名：`nitro curl`）。

```sh
npx nitro fetch [url] [--dir <dir>] [--no-dev] [--envName <name>] [curl options]
```

URL 可以是路径（例如 `/api/hello`，会相对于 `http://localhost` 解析），也可以是以 `http://` 或 `https://` 开头的完整 URL。默认值为 `/`。URL 的主机名会作为 `host` 标头发送（除非使用 `-H` 设置），因此服务器可以获取该值。项目根目录只能通过 `--dir` 设置，因为位置参数是 URL。

如果项目正在运行 [`nitro dev`](#nitro-dev)（或使用 [Vite 插件](/docs/vite)运行 `vite dev`），请求会发送到该开发服务器，因此会使用当前代码及其开发行为（公共资源、`devProxy` 等），日志也会保留在开发服务器终端中。否则，命令会像 [`nitro serve`](#nitro-serve) 一样启动服务器（生产模式，加载 `.env.production` 和 `.env` 文件），在响应后运行 `close` 钩子并关闭服务器。使用 `--no-dev` 可始终启动服务器。指定 `--envName` 时，只有开发服务器的环境名称相同才会使用它（默认为 `development`，除非通过 `nitro dev --envName` 设置）。Vite 只接受其 [`server.allowedHosts`](https://vite.dev/config/server-options#server-allowedhosts) 选项中列出的主机（以及 `localhost`）。

响应体会在到达时流式写入 stdout，日志则写入 stderr，因此可以通过管道传递输出（`nitro fetch /api/users | jq`）。

支持部分 curl 选项：

| 标志 | 描述 |
| --- | --- |
| `-X`、`--request` | 请求方法（默认为 `GET`；带请求体时为 `POST`；使用 `--head` 时为 `HEAD`）。 |
| `-H`、`--header` | 请求标头（`Name: value`），可重复指定（包括重复使用同一名称）。`Name:` 会移除默认标头。 |
| `-d`、`--data` | 请求体，按 `application/x-www-form-urlencoded` 发送（除非通过 `-H` 设置）。`@file` 会读取文件（不包含换行符），`@-` 会读取 stdin。重复的值会以 `&` 连接。 |
| `--data-raw` | 与 `--data` 相同，但不处理 `@`。 |
| `--data-binary` | 与 `--data` 相同，但会保留文件内容原样。 |
| `--json` | JSON 请求体（`@file` 和 `@-` 会原样读取），并将 `content-type` 和 `accept` 标头设为 `application/json`。 |
| `-i`、`--include` | 在输出中包含响应状态行和标头。 |
| `-I`、`--head` | 发送 `HEAD` 请求，只打印响应状态行和标头。 |
| `-o`、`--output` | 将响应写入文件，而不是 stdout。 |
| `-s`、`--silent` | 隐藏 Nitro 日志（不包括应用日志）和错误消息。 |
| `-v`、`--verbose` | 打印请求与响应标头以及 Nitro 信息日志（写入 stderr）。 |

不会跟随重定向。响应状态为 `4xx` 或 `5xx` 时，会打印响应体并以代码 `22` 退出（类似 `curl --fail-with-body`）。如果无法写入输出（例如 stdout 提前关闭：`nitro fetch | head`），命令会停止并以代码 `23` 退出。收到 `SIGINT` 或 `SIGTERM` 时，会停止并以代码 `130` 或 `143` 退出。其他错误以代码 `1` 退出，无效参数以代码 `2` 退出。退出前始终会关闭服务器并运行 `close` 钩子。

::warning
不使用构建器运行目前处于实验阶段。打包器选项和通过 `build:config` 钩子添加的插件不会生效，详情请参阅 [`builder`](/config/build#builder)。
::

**示例：**

```sh
npx nitro fetch /api/hello
npx nitro curl -i -X POST /api/users --json '{"name":"nitro"}'
```

## `nitro deploy`

构建项目，然后运行所选 preset 的部署命令。

```sh
npx nitro deploy [--dir <dir>] [--prebuilt] [build flags...] [-- <extra deploy args>]
```

| 标志 | 描述 |
| --- | --- |
| `--prebuilt` | 跳过构建步骤并部署现有构建输出，使用该构建输出对应的预设和环境名称。 |

所有 [`nitro build`](#nitro-build) 标志（`--preset`、`--minify`、`--builder`、`--compatibility-date`、`--envName` 等）也会被接受，并应用于构建步骤。`--` 后的参数会附加到底层部署命令（或作为 `args` 传递给函数部署命令）。

::note
并非所有 preset 都支持 `nitro deploy`。如果所选 preset 未定义部署命令（或未找到构建输出），命令会报错失败。在这种情况下，请使用其他 preset，在 Nitro 配置中配置部署命令，或按照提供商的[部署指南](/deploy)手动部署。
::

**示例：**

```sh
# 使用 cloudflare_module preset 构建，然后运行 wrangler deploy
npx nitro deploy --preset cloudflare_module

# 部署现有构建，而不重新构建
npx nitro deploy --prebuilt
```

## `nitro task`

操作 [Nitro 任务](/docs/tasks)（实验性功能）。

::important
任务支持处于实验阶段，需要使用 `experimental.tasks` 标志。`task` 子命令针对**当前正在运行的开发服务器**执行，因此请在 `nitro dev` 运行时于第二个终端中执行这些命令。详情请参阅[任务文档](/docs/tasks)。
::

### `nitro task list`

列出可用任务及其描述。

```sh
npx nitro task list [--dir <dir>]
```

| 标志 | 描述 |
| --- | --- |
| `--dir` | 项目根目录。 |

### `nitro task run`

按名称运行任务，也可以选择传入 JSON 负载。

```sh
npx nitro task run <name> [--dir <dir>] [--payload <json>]
```

| 标志 | 描述 |
| --- | --- |
| `--dir` | 项目根目录。 |
| `--payload` | 解析为 JSON 字符串，并作为负载传递给任务。 |

**示例：**

```sh
npx nitro task run db:migrate --payload '{"force": true}'
```

## `nitro docs`

在浏览器中打开 Nitro 文档（[nitro.build](https://nitro.build)），也可以指定要打开的页面路径（例如 `/docs/routing`）。

```sh
npx nitro docs [page]
```
